為什麼 AI Token 成本這麼難控制？

在介紹工具之前，我們先理解 AI token 成本難以控制的根本原因：

1. Token 消耗的複雜性

  • Input ≠ 你看到的輸入：每次 API 請求都包含 system prompt + chat history + user input，實際 token 數往往是表面輸入的 3-10 倍
  • Output 不可預測：模型輸出長度受 temperature、top-p、max_tokens 設定影響，難以預估
  • Context window 的代價：更大的 context = 更高的每次請求成本（例如 1M context 的 Haiku 5.5 長文定價比標準定價貴 5 倍）

2. 多模型、多服務商的碎片化

企業通常同時使用多個 AI 服務：

  • OpenAI（GPT-6.1 Sol / GPT-5.5 Mini）
  • Anthropic（Claude Opus / Sonnet / Haiku）
  • Google（Gemini 4 Argon / Flash）
  • 自架開源（Mistral / Qwen / DeepSeek）

這些服務商的計費方式、token 計算邏輯、dashboard 各不相同，難以統一管理。

3. 缺乏跨部門可視化

工程部門、產品部門、客服部門各自使用 AI，但財務部門只看到一張 API 帳單，無法追溯每個功能的 ROI。

LangFuse：最受歡迎的開源 LLM Observability

LangFuse 是目前最受歡迎的開源 LLM observability 工具，GitHub 超過 15K★，支援 OpenAI / Anthropic / Google / 自架模型的統一監控。

核心功能

  • Trace 追蹤：記錄每個 LLM 請求的完整生命週期（input → prompt → output → cost）
  • Cost Breakdown：按模型、按用戶、按 session、按日期統計 token 使用量與費用
  • Prompt Management：集中管理所有 system prompt，版本控制，A/B testing
  • Evaluation：自動評估 LLM 輸出品質（accuracy、relevance、faithfulness）
  • Dataset：建立測試集，持續監控模型性能退化

自架安裝（Docker）

git clone https://github.com/langfuse/langfuse
cd langfuse
docker compose up -d

預設服務在 http://localhost:3000，PostgreSQL 資料庫自動配置。

LiteLLM：免費自架 AI Gateway

LiteLLM 是開源 AI Gateway，統一 100+ LLM providers 的 API，提供統一的 OpenAI 相容介面。GitHub 超過 20K★，是企業控制 AI 成本的核心基礎設施。

核心功能

  • Unified API：一套程式碼同時呼叫 OpenAI / Anthropic / Gemini / Mistral / 自架模型
  • Model Routing：根據成本、延遲、可用性自動路由請求至最適合的模型
  • Budget Management：設定每個用戶 / 每個 team / 每個 model 的 token 預算上限
  • Fallback：主要模型超限或出錯時自動切換至備用模型
  • Caching：相同輸入自動快取輸出，節省重複計費
  • Rate Limiting：防止單一用戶/功能消耗過多資源

成本節省實例

案例：台灣電商客服 AI 部署

  • 問題：每個客服問題都送 Claude Sonnet 5.5（$1.00/$3.00/1M），月帳單 $8,000

    • 簡單問題（分類 confidence >90%）→ Claude Haiku 5.5（$0.10/$0.50/1M）
    • 中等問題 → Claude Sonnet 5.5
    • 複雜問題 → Claude Opus 5.5
  • 結果：月帳單從 $8,000 降至 $2,400（70% 節省）

企業 AI 成本控制策略框架

根據 Uber / Meta / Microsoft 的失敗案例，我們整理了一個可立即執行的 AI 成本控制框架：

第一步：可視化（第 1-2 週）

  • 部署 LangFuse 或整合 API provider 的原生 billing dashboard
  • 建立 cost breakdown：按模型 / 按功能 / 按部門 / 按時段
  • 識別 top 3 最貴的 API endpoints（通常佔 70% 總成本）

第二步：設定預算警報（第 1-2 週）

  • 設定每日 / 每週 / 每月 token 預算上限
  • 設定異常警報（e.g., 單日成本超過前 7 天平均的 200%）
  • 設定每個 API key 的個別預算（防止單一功能失控）

第三步：模型路由優化（第 3-4 週）

  • 分析現有請求的複雜度分布
  • 設定 LiteLLM routing 規則：簡單任務 → 便宜模型
  • 目標：70% 請求使用 Haiku 5.5 / Gemini Flash，20% 使用 Sonnet，10% 使用 Opus

第四步：Prompt + Cache 優化（第 5-8 週）

  • 系統 prompt 最短化（每縮短 1K tokens × 每日 10K 請求 = 節省 10M tokens/月）
  • 啟用 Semantic Cache（相似問題返回快取結果）
  • 對靜態知識庫啟用 Prompt Caching（Anthropic / Google 均提供大幅折扣）

第五步：長期自架評估（第 2-3 個月）

  • 當月 API 成本 > $10,000 時，評估自架成本效益
  • 優先考慮：Mistral Large 4（Oct 27 開源）/ Qwen 3.8 Flash Next / DeepSeek V4
  • 混合架構：自架模型處理 80% 一般請求，API 處理 20% 高難度請求

預期成果

  • 第 1 個月：可視化 + 預算警報 → 防止超支，節省 10-20%
  • 第 2 個月：模型路由 → 節省 40-70%
  • 第 3 個月：Prompt + Cache 優化 → 再節省 20-30%
  • 第 4-6 個月：自架評估 → 總計節省 70-90%
