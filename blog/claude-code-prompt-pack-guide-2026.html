免費試讀：10 個精選 Prompt

以下是完整包裡最常用的 10 個，直接複製使用。

1. 函式拆分（單一職責原則）

以下函式太長、職責不清。請根據單一職責原則（SRP）拆分重構：

[貼上過長的函式]

要求：
1. 將函式拆成 3-6 個小函式，每個函式只做一件事
2. 命名要明確表達意圖（動詞+名詞，例如 validateUserEmail）
3. 保留所有原始功能，不引入 bug
4. 用 TypeScript 介面定義各函式的輸入/輸出型別
5. 寫一個主函式組合所有子函式
6. 附上重構前後的複雜度對比說明

2. OpenAPI 文件生成

根據以下 API 路由程式碼，生成完整的 OpenAPI 3.0 規格文件：

[貼上 Express / Fastify 路由程式碼]

要求：
1. 輸出完整的 openapi.yaml（3.0 規格）
2. 包含所有端點的 path、method、description
3. 定義所有 request body 和 query params schema
4. 定義所有 response schema（成功和錯誤）
5. 加入 security scheme（JWT Bearer / API Key）
6. 為每個端點加上一個 curl 範例

3. Memory Leak 診斷

症狀：[記憶體成長曲線，例如：每小時增加 200MB]

[貼上疑似有問題的程式碼模組]

要求：
1. 識別常見 memory leak 模式（event listeners、closure、global cache）
2. 標出每個疑點並解釋為何會洩漏
3. 提供修復方案（移除 listeners、使用 WeakMap、限制 cache 大小）
4. 建議記憶體監控工具和檢測方法
5. 提供一個簡化的測試腳本驗證修復

[貼上 React component 程式碼]

3. 測試使用者互動（按鈕點擊、表單輸入）
4. 測試異步資料載入（loading、success、error 狀態）
5. Mock 所有 API 呼叫和 context
6. 遵循 Testing Library 最佳實踐（用 role 查找元素）

2. 建議拆分成哪些 microservices（3-8 個為宜）
3. 定義每個 service 的職責邊界
4. 設計 service 間通訊（REST、gRPC、Message Queue）
5. 標出 strangler fig pattern 的遷移路徑
6. 評估拆分的利弊（複雜度 vs 可擴展性）

2. 找出效能瓶頸點

4. 實作最適合當前場景的方案
5. 量化優化效益（例如：O(n²) → O(n log n)）

4. 建議需要建立的索引（附 CREATE INDEX 語法）

使用技巧：讓 Prompt 效果最大化

技巧 1：給範例比給規則更有效

與其說「用好的命名」，不如說「用 validateUserEmail 這種格式命名」。模板裡的要求都已經是具體例子，不是抽象規則。

技巧 2：分批執行長任務

系統架構類的 Prompt 很長，Claude Code 有時會在中途停下來。遇到這種情況，用「繼續」或「請繼續完成第 X 點」讓它接著做，不要重新問。

技巧 3：先問診斷再要修復

Bug 修復類的 Prompt 都設計成「先列原因再給方案」的結構。不要直接問「幫我修這個 bug」——先問分析，確認根因後再要修復，結果品質差很多。

技巧 4：加入你的 context

每個模板都有 [方括號] 佔位符，一定要填。特別是「環境」「資料規模」「現有架構」這幾個欄位——填得越具體，輸出越精準。
