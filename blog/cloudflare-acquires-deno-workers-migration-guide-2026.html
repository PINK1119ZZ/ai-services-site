重大新聞：Cloudflare 宣布收購 Deno

2026 年 10 月 9 日，Cloudflare 官方部落格宣布收購 Deno——這是 JavaScript/TypeScript 執行環境與邊緣運算領域近年來最震撼的整併案之一。此消息在 Hacker News 上迅速衝至首頁，獲得超過 960 個 upvote，成為近期最熱議的開發者話題之一。

Deno 由 Node.js 創始人 Ryan Dahl 於 2018 年創立，以「修正 Node.js 設計錯誤」為目標。相較於 Node.js，Deno 提供原生 TypeScript 支援、更嚴格的安全模型（需明確授予許可）、內建標準函式庫，以及與 Web 標準 API 更高的相容性。

Deno Deploy 則是 Deno 公司於 2021 年推出的邊緣運算平台——類似 Cloudflare Workers，讓開發者可以把 Deno 程式碼部署到全球 35 個 PoP（Points of Presence），實現超低延遲的邊緣執行。

這次收購代表兩個方向的整合：Deno 的技術能力（尤其是 TypeScript 原生支援與 Web 標準相容性）將融入 Cloudflare Workers 生態，而 Deno Deploy 的現有用戶則必須在 6 個月內完成遷移。

⚠️ 如果你正在使用 Deno Deploy： 請立即確認你的應用，Deno Deploy 將於 2027 年 4 月前後正式關閉。Cloudflare 提供遷移工具，但你需要主動行動。

為什麼 Cloudflare 要收購 Deno？

要理解這次收購的戰略邏輯，需要先看 Cloudflare 的長期佈局。

Cloudflare Workers 的技術債

Cloudflare Workers 自 2017 年推出以來，一直使用 V8 引擎（JavaScript 引擎）加上自行開發的 Workers Runtime。這個架構效能很好，但在 TypeScript 支援、Web 標準相容性方面一直落後於 Deno。

開發者常見的痛點包括：

  • TypeScript 需要額外的 build step，不像 Deno 可以直接執行 .ts 檔案
  • 部分 Web API（如 Streams、Fetch 的細節行為）與瀏覽器標準有微妙差異
  • Package 管理依賴 npm，與 Deno 的 URL import 模式衝突

Deno 的強項與財務困境

Deno 的技術口碑很好，但商業化一直是挑戰。Deno Deploy 用戶增長雖然穩定，但 Free tier 佔比過高，付費轉換率不理想。在 VC 資金緊縮的 2025-2026 年環境下，Deno 公司面臨盈利壓力。

對 Cloudflare 來說，這是一個典型的「技術收購」——買的不是用戶，而是 Deno 的核心 Runtime 技術、Ryan Dahl 團隊，以及更重要的：一套已被市場驗證的 TypeScript-first 開發體驗。

競爭格局：對抗 Vercel + Bun 組合

Vercel 已與 Next.js 深度整合，Bun 的崛起讓執行環境競爭更加激烈。Cloudflare 收購 Deno，等於在邊緣運算戰場建立更強的技術護城河，直接與 Vercel Edge Functions 形成更全面的競爭。

Deno Deploy 關閉時間軸

根據 Cloudflare 官方聲明，遷移時間軸如下：

時間點 事件
2026 年 10 月 9 日 收購宣布，遷移工具開放測試
2026 年 10-12 月 遷移期：Deno Deploy 繼續正常運作，開發者可開始遷移
2027 年 1 月 Deno Deploy 停止接受新用戶
2027 年 4 月（預估） Deno Deploy 正式關閉

Cloudflare 承諾提供遷移工具，並對 Deno Deploy 付費用戶提供等值的 Workers 免費點數作為補償。Free tier 用戶則可直接使用 Workers 的免費額度。

技術差異：Deno Deploy vs Cloudflare Workers

在遷移之前，必須先理解兩個平台的核心差異：

面向 Deno Deploy Cloudflare Workers
執行環境 Deno Runtime（V8 + Deno APIs） Workers Runtime（V8 + Web APIs）
TypeScript 支援 原生，無需 build step 需要 wrangler build（即將改善）
Package 管理 URL import + JSR + npm compat npm（透過 wrangler）
儲存 Deno KV（全球一致性） Workers KV + D1 + R2
PoP 數量 35 個節點 300+ 個節點
CPU 時間限制 50ms（Free） 10ms（Free）/ 無限（Paid）
Free 月請求量 100 萬次 100 萬次
Cron Jobs 原生支援 Workers Cron Triggers

最重要的差異是 CPU 時間限制：Deno Deploy Free tier 允許 50ms，Workers Free 只有 10ms。如果你的 Worker 邏輯比較複雜，可能需要升級到 Workers Paid 計畫（$5/月起）。

完整遷移指南：手把手從 Deno Deploy 移到 Workers

步驟 1：安裝 Wrangler CLI

# 安裝 Wrangler（Cloudflare Workers CLI）
npm install -g wrangler

# 登入 Cloudflare 帳號
wrangler login

步驟 2：建立新的 Worker 專案

# 從 template 建立 TypeScript Worker
npm create cloudflare@latest my-worker -- --type typescript

cd my-worker

步驟 3：轉換 Deno Deploy 入口點

Deno Deploy 使用 Deno.serve()，Workers 使用 export default { fetch() }：

// --- Deno Deploy (舊) ---
Deno.serve(async (req: Request): Promise<Response> => {
  const url = new URL(req.url);
  if (url.pathname === "/api/hello") {
    return new Response(JSON.stringify({ message: "Hello!" }), {
      headers: { "Content-Type": "application/json" },
    });
  }
  return new Response("Not Found", { status: 404 });
});

// --- Cloudflare Workers (新) ---
export default {
  async fetch(request: Request, env: Env): Promise<Response> {
    const url = new URL(request.url);
    if (url.pathname === "/api/hello") {
      return new Response(JSON.stringify({ message: "Hello!" }), {
        headers: { "Content-Type": "application/json" },
      });
    }
    return new Response("Not Found", { status: 404 });
  },
};

關鍵變化：

  • Deno.serve(handler) → export default { fetch(request, env) }
  • 多了 env 參數（用來存取 KV、R2、環境變數）
  • TypeScript 需要定義 Env interface

步驟 4：處理 URL Import

Deno 可以直接 import URL，Workers 不行。需要改用 npm 或 JSR：

// Deno Deploy (舊)
import { Hono } from "https://deno.land/x/hono/mod.ts";

// Cloudflare Workers (新)
// 先 npm install hono
import { Hono } from "hono";

步驟 5：wrangler.toml 設定

# wrangler.toml
name = "my-worker"
main = "src/index.ts"
compatibility_date = "2026-10-01"
compatibility_flags = ["nodejs_compat"]

# 若有 Cron Jobs（對應 Deno Deploy Scheduled）
[triggers]
crons = ["0 */6 * * *"]  # 每 6 小時執行一次

步驟 6：部署

# 本地開發
wrangler dev

# 部署到 Production
wrangler deploy

KV 與 R2 遷移：儲存層對應

Deno Deploy 使用 Deno KV——一個全球一致的 key-value store，類似 Cloudflare Workers KV 但有全域即時一致性（Workers KV 是最終一致性）。

Deno KV → Workers KV 遷移

// Deno KV (舊)
const kv = await Deno.openKv();
await kv.set(["users", userId], userData);
const result = await kv.get(["users", userId]);

// Workers KV (新) — 需要在 wrangler.toml 定義 KV namespace
// wrangler.toml: [[kv_namespaces]] binding = "USERS_KV" id = "..."
await env.USERS_KV.put(`user:${userId}`, JSON.stringify(userData));
const raw = await env.USERS_KV.get(`user:${userId}`);
const result = raw ? JSON.parse(raw) : null;

注意： Deno KV 支援複合 key（array of primitives），Workers KV 只支援字串 key。遷移時需要手動把 Deno KV 的 key array 序列化成字串（如用 `:` 分隔）。

Deno KV → D1（關聯式資料需求）

如果你的資料有關聯關係，考慮遷移到 Cloudflare D1（SQLite）：

// D1 範例（Workers）
const { results } = await env.DB.prepare(
  "SELECT * FROM users WHERE id = ?"
).bind(userId).all();

const user = results[0];

Cloudflare 也提供官方遷移工具，可以把 Deno KV 資料匯出為 JSON，再批次寫入 Workers KV 或 D1。

Runtime 相容性：Deno API 在 Workers 上怎麼跑

好消息是 Workers 的 Web 標準相容性近年來大幅提升，大部分基本 Deno API 都有對應：

Deno API Workers 對應 狀態
fetch() fetch() ✅ 直接相容
Request / Response Request / Response ✅ 直接相容
crypto.subtle crypto.subtle ✅ 直接相容
Deno.env.get() env.MY_VAR（wrangler vars） ⚠️ 需調整
Deno.readFile() 無本地檔案系統，用 R2 ❌ 需重設計
WebSocket Workers WebSocket Hibernation ✅ Workers 版更強

最需要注意的是 本地檔案系統存取——Workers 和 Deno Deploy 都是 serverless，但 Deno Deploy 部分版本允許讀取 bundle 內的靜態檔案。Workers 建議把靜態資源放到 Cloudflare R2，或用 Workers Assets 功能。

對 JavaScript 生態系的深遠影響

這次收購不只是一個平台整合，更有可能重塑 JavaScript 邊緣運算的格局。

正面影響

  • Workers 的 TypeScript 體驗將大幅提升： Deno 的原生 TS 支援技術將被整合進 Workers Runtime，預計 2027 上半年發布
  • Web 標準推進加速： Deno 一直是 WinterCG（Web-interoperable Runtimes Community Group）的推動者，加入 Cloudflare 後有更多資源
  • 開發者工具改善： Deno 的 LSP（Language Server Protocol）整合可能帶進 VS Code Workers 開發體驗

疑慮

  • 開源性： Deno 是開源的（MIT），Cloudflare Workers Runtime 則是閉源的。Deno 的部分技術被整合後，開源承諾能否延續？
  • Ryan Dahl 的角色： 收購後 Ryan Dahl 將加入 Cloudflare，但他是否會繼續主導技術方向，還是逐漸邊緣化？
  • 競爭格局失衡： Cloudflare Workers 已是邊緣運算市佔第一，吃掉 Deno Deploy 後，有沒有其他選手能挑戰？

對 Bun 的影響

Bun 近年快速成長，定位是「更快的 Node.js」。Deno 消失後（Deno Deploy 關閉），不少 Deno Deploy 用戶可能轉向 Bun 或 Fly.io，而非全部流入 Workers。這對 Bun 是個機會。

結論：現在該怎麼做？

如果你是 Deno Deploy 用戶

  1. 立即清查你的應用：有哪些用了 Deno Deploy？有幾個 project？
  2. 評估遷移複雜度：純 HTTP handler 最簡單，有 Deno KV 資料的比較複雜
  3. 優先遷移生產環境：6 個月的窗口看起來長，但生產環境的遷移往往需要多輪測試，建議 2 個月內完成
  4. 善用 Cloudflare 提供的遷移工具：官方會提供 CLI 工具協助資料匯出

如果你還在評估邊緣運算平台

這次事件再次提醒：免費的 serverless 平台都有被收購或關閉的風險。在 Cloudflare Workers 上建置的優點是：Cloudflare 是一家財務健全的公司，短期內不存在這個問題。

對於需要更彈性的架構，或是資料不能放在美國公司服務的專案，自架 VPS（如 DigitalOcean 或 Cloudways）搭配 Deno/Bun 仍是一個好選項。
