一個讓 HN 社群討論最久的問題：「這真的是 Google 官方的嗎？」

當 google/ax 在 2026 年 9 月 21 日登上 Hacker News #2 時，討論串裡有一個問題被反覆問：「這是 Google 官方支持的專案，還是又一個 Google Lab 的附屬側專案？」

答案讓很多人訝異：是的，這是官方的。

幾個具體證據：repo 在 github.com/google（不是 googlecloudplatform 或 google-research）、沒有附上 Google 慣用的「not officially supported」免責聲明、Apache 2.0 授權（Google 官方開源的標準選擇）、repo 描述直接寫「Google's open agentic orchestration runtime」。

這個細節很重要，因為它影響你對這個工具長期維護性的判斷。

AX 是什麼？用一句話說清楚

AX 是一個讓你用 YAML 宣告式定義和運行 AI Agent 任務的框架，底層跑在 Kubernetes 上。

如果你熟悉 Kubernetes，可以這樣理解：

  • Kubernetes 讓你用 YAML 定義「我要跑哪些 container、怎麼擴縮、怎麼網路互通」
  • AX 讓你用 YAML 定義「我要跑哪些 AI Agent、任務流程怎麼串接、用哪個 LLM、在什麼 Workspace 裡執行」

核心問題從「如何管理容器」變成「如何管理 Agent 任務」，但基礎設施抽象層的思路是一樣的。

AX 的技術架構：四個核心原語

AX 建立在四個基本概念（primitives）之上：

1. Task（任務）

Task 是 AX 裡最基礎的執行單元。它代表一個 Agent 需要完成的具體工作，例如「閱讀這份 repo 的 README 然後寫一份技術分析報告」或「執行這段程式碼並驗證輸出結果」。

每個 Task 有自己的狀態機：Suspended → Pending → Running → Succeeded/Failed。預設新建的 Task 是 Suspended 狀態，需要顯式 resume 才會開始執行（防止意外觸發）。

2. Workspace（工作空間）

Workspace 是 Task 執行時的環境容器。它定義了 Agent 能存取哪些資料、哪些工具、哪些檔案系統。可以把它想成一個「有邊界的沙盒」——Agent 在 Workspace 裡工作，不會意外觸碰到 Workspace 外的資源。

AX 的 Workspace 支援 inlined files（直接在 YAML 裡嵌入檔案內容）和外部掛載，這讓版本控制和審計變得容易。

3. Gateway（閘道）

Gateway 是 AX 的控制面入口。你透過 Gateway 部署 Task、查詢狀態、接收 callback。AX CLI 的所有操作（ax apply、ax get tasks）都是和 Gateway 通訊。

Gateway 也負責授權管理——你可以配置誰可以部署哪些類型的 Task，對多人協作或企業 CI/CD 整合很重要。

4. Model（模型）

Model 定義 Task 使用哪個 LLM 後端。AX 目前主要支援 Google 的 Gemini 系列，但架構上設計為可插拔，社群有嘗試接入其他 provider 的 PR。

AX 的技術特點：Agent Substrate 運行時

AX 的底層是 Google 稱為 Agent Substrate 的計算運行時，源自 Google DeepMind 的 agentic 研究基礎設施。這個設計有幾個值得注意的特點：

密集多工（Dense Multiplexing）

傳統的任務調度通常是「一個任務一個容器」，每個任務預留固定的 CPU/記憶體資源。AX 的 Agent Substrate 使用密集多工：多個 Agent Task 共享 worker 資源，透過輕量級 actor 模型管理，而不是每個 Task 獨占一個 VM 或 container。

這讓 AX 聲稱可以在單個叢集上運行「數十億並發 Agent 任務」——雖然這個數字需要在實際負載下驗證，但架構設計的確支援超高密度。

Sub-second Suspend/Resume

Agent 任務通常有長時間的「等待」：等待 LLM API 回應、等待工具執行、等待人工確認。傳統框架在等待期間佔用資源。AX 設計了毫秒級的 suspend/resume 機制——Agent 在等待時可以被暫停並讓出資源，收到回應後立即恢復，整個過程對 Agent 邏輯透明。

Kubernetes Native

AX 不是「執行在 Kubernetes 上的服務」，而是「AX 的控制面 IS Kubernetes」。Task、Workspace、Gateway 都作為 Kubernetes Custom Resources（CRD）存在，可以用 kubectl 查詢和管理。

快速上手：部署你的第一個 AX Task

前置需求

  • 一個 Kubernetes 叢集（本地 minikube / kind，或 GKE）
  • kubectl 已配置
  • Gemini API 金鑰（Model 設定需要）
  • Go 1.23+（如果要從 source 編譯 AX CLI）

Step 1：部署 AX 控制面

# 克隆 repo
git clone https://github.com/google/ax
cd ax

# 部署 AX CRDs 和 control plane 到 Kubernetes
kubectl apply -f deploy/

# 確認 Gateway 已啟動
kubectl get pods -n ax-system

Step 2：配置 Model

apiVersion: ax.agentexecutor.io/v1alpha1
kind: Model
metadata:
  name: gemini-4-argon
spec:
  provider: google
  modelId: gemini-4-argon
  apiKeySecretRef:
    name: gemini-api-key
    key: api-key
kubectl apply -f model.yaml

Step 3：定義 Workspace

apiVersion: ax.agentexecutor.io/v1alpha1
kind: Workspace
metadata:
  name: code-review-ws
spec:
  files:
    inline:
      - path: "guidelines.md"
        content: |
          # Code Review Guidelines
          - Check for security vulnerabilities
          - Verify test coverage
          - Review API documentation

Step 4：建立並執行 Task

apiVersion: ax.agentexecutor.io/v1alpha1
kind: Task
metadata:
  name: review-pr-123
spec:
  workspaceRef:
    name: code-review-ws
  modelRef:
    name: gemini-4-argon
  prompt: |
    Review the following code diff and provide structured feedback
    based on the guidelines in the workspace.
    Focus on: security, performance, and maintainability.
    [diff content here]
  # 注意：新 Task 預設 Suspended，需要 resume
  suspend: false
# 部署 Task
kubectl apply -f task.yaml

# 查詢執行狀態
kubectl get tasks -n default
kubectl describe task review-pr-123

Step 5：使用 AX CLI

# 安裝 AX CLI（Go 1.23+ 需要）
go install github.com/google/ax/cmd/ax@latest

# 部署（等同 kubectl apply，但有 AX 特定驗證）
ax apply -f task.yaml

# 查詢 Task 列表
ax get tasks

# 查看 Task 日誌
ax logs task/review-pr-123

# Resume 暫停的 Task
ax resume task/review-pr-123

AX vs 其他 Agent 編排框架：橫向比較

框架 定位 基礎設施 授權 適合場景
Google AX 生產級 K8s 原生 Kubernetes Apache 2.0 企業大規模 Agent 部署
LangGraph Graph-based Agent 流程 無特定 MIT 複雜多步 Agent 流程設計
CrewAI 角色分工多 Agent 無特定 MIT 多 Agent 協作任務
OpenClaw Personal AI runtime Node-based 商業 個人/小團隊 AI 助理
Scion（GCP） K8s + harness 整合 GKE Apache 2.0 包裝既有 agent harness

AX 最明顯的差異點是：它是基礎設施層，不是應用層。LangGraph 幫你設計「Agent 要怎麼思考」，AX 幫你解決「Agent 任務要怎麼運行、擴縮、監控」。兩者可以結合使用：用 LangGraph 設計 Agent 邏輯，用 AX 作為運行時。

AX 的現實限制

AX 目前仍是早期階段（最新版本 v0.3.x），有幾個實際使用需要考量的問題：

1. 主要支援 Gemini

AX 的 Model primitive 目前官方支援主要是 Google 的 Gemini 系列。如果你的 stack 是 Claude 或 OpenAI，需要等待或自行實作 provider adapter。社群有相關 issue，但尚未有合併的 PR。

2. 需要 Kubernetes 專業知識

AX 的「Kubernetes native」特性是雙刃劍。它讓有 K8s 背景的 DevOps 很自然，但對沒有 K8s 經驗的 AI 工程師來說，學習曲線陡峭。這不是一個「pip install 就能跑」的框架。

3. 文件仍不完整

目前 agentexecutor.io 的官方文件覆蓋基礎概念，但進階使用（複雜 Workspace 配置、Gateway 安全設置、multi-cluster 部署）的文件還很薄弱。

4. 並發規模宣稱需驗證

「每叢集數十億並發 Agent 任務」是 AX 的官方宣稱，但目前尚無獨立的公開 benchmark。實際的規模上限取決於 K8s 叢集配置和 LLM API 的 rate limits。

誰應該現在就認真研究 AX？

應該馬上深入的：

  • 在企業環境管理 10+ 個 AI Agent 工作流的平台工程師
  • 已有 GKE 或 Kubernetes 基礎設施的 ML 平台團隊
  • 在研究 agentic AI 基礎設施設計的架構師
  • Google Cloud 客戶——AX 長期很可能深度整合進 GKE/Vertex AI

可以繼續觀望的：

  • 個人開發者跑小規模 Agent 工作流
  • 不使用 Kubernetes 的團隊（除非你打算遷移）
  • 需要 Claude/GPT 作為主要 LLM 的場景（等社群 adapter 成熟）

AX 與 Google 的更大佈局：Scion 的關係

在 HN 討論中，一個評論者提到了另一個 Google Cloud 專案：Scion（googlecloudplatform/scion）。它被描述為「更成熟、更整合的選項，包裝既有 agent harness（如 OpenCode 插件）而不需要採用完整 Agent Substrate stack」。

這兩個專案的關係目前還不完全清楚，但一個可能的框架是：

  • AX：底層 Agent 運行時基礎設施，適合從頭建立
  • Scion：更上層的整合層，適合把既有 Agent harness 遷移到 GCP

如果你的目標是在 GCP 上跑大規模 Agent，可能值得同時研究這兩個專案後再做選擇。

總結：AX 是下一代 AI 基礎設施的重要參考

即使你現在不打算部署 AX，它仍然值得你花時間理解，原因有三：

1. 它定義了「AI Agent 基礎設施」應該長什麼樣子。Task、Workspace、Gateway、Model 這四個原語不只是 AX 的設計，而是思考「如何管理大規模 Agent 系統」的一個成熟框架。

2. Google 的技術選擇往往成為業界標準。Kubernetes 本身就是 Google Borg 的開源版本。AX 是否會成為 Agent 編排的 Kubernetes，值得密切關注。

3. 如果你在 GCP 生態，AX 整合進 GKE/Vertex 只是時間問題。現在提前了解，能讓你在它成為標配時有技術優勢。

從純實用角度：如果你今天需要運行生產級 multi-agent 工作流，LangGraph + 現有雲端服務可能是更快的路徑。但如果你在做中長期的 AI 平台規劃，AX 值得列入你的技術雷達。
