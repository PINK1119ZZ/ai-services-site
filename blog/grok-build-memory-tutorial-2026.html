為什麼 Grok Build 記憶功能是大事？

對於每天使用 AI Coding Agent 的開發者，最大的摩擦之一就是「每次開新對話，都要重新介紹自己」。你用 Next.js 14，你喜歡 functional components，你的資料庫是 Postgres，你不喜歡 Lodash——這些設定每次都要重新說，不只浪費 token，更打斷心流。

Claude Code 用戶對此的解法是維護 CLAUDE.md 檔案，手動撰寫專案背景給 Agent 讀取。這個方法有效，但需要開發者主動維護，本質上是「人在管 AI 的記憶」。

Grok Build v1.0.34 做了一件不同的事：讓 Agent 自己管自己的記憶。Agent 會在對話過程中主動觀察、自動整理、以 markdown 格式儲存你的偏好，並在下次對話時自動載入。這種「Agent 驅動的記憶管理」是一個概念上的跳躍。

✅ Grok Build v1.0.34 記憶功能核心亮點
  • 自動觀察與儲存：Agent 主動記住你的偏好，無需手動設定
  • Markdown 格式：記憶以可讀的 .md 格式儲存，人類可直接閱讀和理解
  • 雙層作用域：Project Scope（專案專屬）+ Global Scope（跨所有專案）
  • /memory 指令：隨時查看、編輯、刪除記憶條目
  • /dream 指令：觸發記憶整合，整理當前會話的新學習
  • 免費版可用：v1.0.34 更新後所有 Grok Build 用戶均可使用

快速上手：5 分鐘啟動 Grok Build 記憶

步驟一：確認版本

在 build.x.ai 登入後，確認版本號為 v1.0.34 或更新。目前 xAI 會自動更新，但如果你看到記憶相關功能不存在，可以嘗試清除快取後重新登入。

步驟二：第一次使用記憶功能

記憶功能是自動啟動的——只要你開始和 Grok Build 正常對話，Agent 就會開始觀察。以下是建議的第一次對話設定方式：

我是台灣的全端開發者，主要使用：
- 框架：Next.js 14（App Router）
- 語言：TypeScript（strict mode）
- 套件管理：pnpm
- 資料庫：PostgreSQL + Prisma ORM
- 部署：Vercel（前端）+ DigitalOcean（後端/worker）
- 測試：Vitest + Testing Library
- 程式風格：functional，避免 class，喜歡 early return

請記住這些偏好，之後的回答都請依照這個技術棧。

Grok Build 會自動將這些資訊整合至 Global Scope 記憶中。

步驟三：使用 /memory 查看記憶

在對話框輸入 /memory，Agent 會顯示目前儲存的所有記憶條目，格式類似：

## 🧠 你的 Grok Build 記憶

### Global Scope（跨所有專案）
- **開發語言**：TypeScript（strict mode）
- **套件管理器**：pnpm
- **程式風格**：functional，early return，避免 class
- **測試框架**：Vitest + Testing Library
- **偏好資料庫**：PostgreSQL + Prisma ORM

### Project Scope（當前專案：my-saas-app）
- **框架**：Next.js 14 App Router
- **部署**：Vercel（前端）+ DigitalOcean（後端）
- **目前進度**：正在實作使用者認證模組

步驟四：使用 /dream 整合記憶

/dream 是 Grok Build 特有的記憶整合指令。當你完成一個較長的工作階段後，輸入 /dream，Agent 會：

  1. 回顧當前會話中發現的新偏好或習慣
  2. 與現有記憶進行比對，避免重複或矛盾
  3. 整合後更新記憶檔案

建議在每次長工作階段結束前執行一次 /dream，讓記憶保持最新狀態。

雙層記憶架構詳解：Project Scope vs Global Scope

Grok Build 的記憶系統設計了兩個層級，這個設計很有智慧：

維度 Global Scope（全局記憶） Project Scope（專案記憶）
適用範圍 所有專案、所有對話 僅限當前開啟的專案
儲存內容 個人偏好、語言習慣、工具偏好、溝通風格 專案架構、當前進度、特定技術決策、TODO
典型範例 「我偏好 TypeScript、pnpm、early return」 「此專案使用 Tailwind v4、Drizzle ORM、部署在 Cloudways」
載入時機 每次開啟 Grok Build 自動載入 開啟對應專案目錄時載入
更新方式 Agent 自動更新 + /dream 整合 Agent 自動更新 + /dream 整合
儲存格式 Markdown（.md） Markdown（.md）

對於在多個客戶專案間切換的自由工作者，或在公司同時維護多個 repo 的工程師來說，這個雙層設計非常實用——你的個人偏好永遠在，但每個專案的脈絡也分開管理，不會互相污染。

Grok Build 記憶功能進階技巧

技巧一：建立分層記憶策略

不要把所有事情都扔給 Global Scope。建議的分層策略：

  • Global（個人身份層）：程式語言偏好、套件管理器、測試框架、溝通語言（繁中或英文）
  • Project（專案脈絡層）：當前 sprint 目標、已完成的功能、待解決的 bug、特定的技術決策理由

明確告訴 Grok Build 哪些資訊屬於哪個層級，可以讓記憶更有組織：

【Global 偏好更新】我從今天開始改用 Bun 替代 Node.js，請記在全局記憶中。
【Project 脈絡更新】這個專案決定不使用 tRPC，改用 REST API，原因是客戶端是 React Native。

技巧二：定期清理記憶

隨著時間推移，記憶可能累積過時資訊。建議每個月執行一次記憶審查：

/memory
# 查看後，針對過時條目：
請刪除關於「使用 Webpack」的記憶，我現在全面改用 Vite 了。

技巧三：用 /dream 建立工作結束儀式

每次完成一個功能或修完一批 bug 後，輸入 /dream 讓 Agent 整理今天學到的內容。這是一個很有價值的工作儀式，類似寫工作日誌，但完全自動化。

技巧四：在新專案開始時主動灌輸脈絡

每次開啟新專案，花 2 分鐘給 Grok Build 一份專案簡介：

新專案開始。請為這個專案建立 Project Scope 記憶：

專案名稱：TaipeiDelivery API
技術棧：Fastify + TypeScript + Prisma + PostgreSQL
部署環境：DigitalOcean Droplet（Ubuntu 22.04）
目前進度：剛建立 repo，開始架構設計
特殊限制：需要支援台灣中文地址格式，時區 Asia/Taipei
合作者：我一個人負責後端，前端由另一名工程師負責

台灣開發者的三大使用場景

場景一：自由工作者多客戶管理

台灣有大量在接案的自由工作者，同時維護 3-5 個客戶專案。每個客戶有不同的技術棧、不同的溝通方式、不同的進度。Grok Build 的 Project Scope 記憶讓你切換專案時，Agent 立刻掌握正確脈絡，不需要每次都解釋「這個客戶用的是 Laravel 不是 Django」。

場景二：AI 產品開發者節省 Token

開發 AI 產品的工程師通常需要大量使用 Coding Agent，Token 成本是重要考量。Grok Build 的記憶功能讓你不需要在每次對話的 system prompt 裡重複貼上大量背景資訊——這直接省下每次對話 500-2,000 個 token，累積起來相當可觀。搭配 Cloudways 部署後端，成本管控更輕鬆。

場景三：企業內部開發團隊統一規範

在企業場景中，Grok Build 的 Global Scope 記憶可以作為個人編碼規範的「自動強制執行層」。每位工程師設定好自己的偏好後，整個 team 的 Grok Build 輸出會更符合公司風格，Code Review 的摩擦大幅減少。

隱私與安全：你需要知道的事

⚠️ 記憶功能使用注意事項
  • 絕對不要在記憶中儲存 API 密鑰、資料庫連線字串、或任何機敏認證資訊
  • Grok Build 記憶儲存在 xAI 雲端，受 xAI 隱私政策約束
  • 如果你的專案有 NDA 或保密協議，評估是否適合讓 AI 儲存專案細節
  • 定期使用 /memory 審查記憶內容，刪除不必要的資訊
  • 離職或專案結束後，記得清除相關的 Project Scope 記憶

相較之下，Claude Code 的 CLAUDE.md 是本地檔案，對隱私敏感的專案（金融、醫療、政府）可能更適合 Claude Code 的本地記憶方案。這是 Grok Build 目前相對 Claude Code 的主要劣勢。

如果你需要 VPN 保護開發環境或在公共場所使用 Grok Build，可以考慮搭配 NordVPN 保護你的網路連線，避免中間人攻擊竊取 API 請求。

Grok Build 記憶功能的限制與未來展望

目前的限制

  • 記憶容量限制：目前尚未公開記憶的最大容量，但 xAI 文件建議保持每個 scope 在 1,000 行以內
  • 雲端依賴：記憶儲存在雲端，離線時無法存取，也增加了隱私風險
  • AI 決策不透明：Agent 自行決定哪些內容值得記憶，有時可能記了不必要的東西，或漏掉重要偏好
  • 無法跨帳號分享：團隊協作時，每個人的記憶是獨立的，無法共享 team-level 的記憶設定
  • 語言偏好需明確設定：預設情況下 Grok Build 可能用英文回覆，台灣用戶需要在 Global Scope 明確設定「請用繁體中文回覆」

未來可期的功能

根據 xAI 的 roadmap 和社群討論，以下功能可能在後續版本出現：

  • Team Scope（團隊共享記憶）：讓整個工程團隊共享專案脈絡
  • 記憶匯出/匯入：支援將記憶備份或在不同帳號間遷移
  • 記憶版本控制：類似 git 的記憶歷史，可以回溯到特定時間點
  • 與本地檔案系統整合：可能提供類似 CLAUDE.md 的本地儲存選項
🆚 結論：Grok Build 記憶功能值得試用嗎？

如果你目前是 Claude Code 或 Cursor 的用戶，但苦於每次都要手動維護記憶設定，Grok Build v1.0.34 的自動記憶功能絕對值得一試——特別是現在免費版就能用。

如果你對隱私有嚴格要求，或需要精確控制 Agent 記住的每一個細節，Claude Code 的 CLAUDE.md 方案仍然是更好的選擇。

兩個工具並非互斥——很多台灣開發者會根據專案性質選擇合適的工具。開放程度高、個人側專案用 Grok Build；客戶專案、機密度高的用 Claude Code。

常見問題 FAQ

Q：Grok Build 和 Grok Chat 是一樣的嗎？

不一樣。Grok Chat 是一般對話介面（grok.x.ai），Grok Build 是專門針對 Coding 任務的 Agentic 環境（build.x.ai），有檔案讀取、程式碼執行、記憶管理等進階功能，更接近 Claude Code 的定位。

Q：/memory 和 /dream 指令在哪裡輸入？

這兩個指令都在 Grok Build 的對話輸入框輸入，就像一般訊息一樣發送，不需要任何特殊設定。

Q：記憶功能會佔用 context window 嗎？

是的，記憶在每次會話開始時會被載入至 context window。但由於 Grok Build 有 500K context window（來自 Grok 4.7 API），即使記憶檔案達到幾千行，仍有充裕的空間給實際的對話內容。

Q：如何完全清除所有記憶？

在對話框輸入以下指令：

請清除我的所有 Global Scope 記憶和當前 Project Scope 記憶。

Agent 會確認後執行清除。如需更細粒度的控制，可以先用 /memory 查看再逐一刪除。

Q：Grok Build 記憶會影響 xAI 的 AI 訓練嗎？

根據 xAI 隱私政策，如果你是付費用戶，可以選擇退出資料用於訓練。免費用戶的對話資料（包含記憶）可能會被用於改善模型。建議前往 xAI 帳號設定確認並調整你的隱私偏好。
