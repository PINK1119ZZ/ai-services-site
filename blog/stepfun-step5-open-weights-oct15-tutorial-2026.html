StepFun 是誰？他們憑什麼有這個規模？

StepFun（階躍星辰）是一家 2023 年成立的中國 AI 公司，核心團隊來自 Google、Baidu 和字節跳動研究院。公司目前大約有 500 名研究員，融資超過 10 億美元，支持者包括阿里巴巴和騰訊。

Step 5 不是他們的第一個大型模型。他們在 2025 年就推出了 Step 3 和 Step 4，逐步建立了大規模 MoE 訓練的工程能力。Step 5 是這個系列的旗艦，代表目前對外公開的最大規模 Chinese open-weight 模型。

更重要的是：StepFun 之前的 Step Flash 系列採用 Apache 2.0 授權。雖然 Step 5 open weights 的授權條款尚未最終確認，但這個先例讓開發者社群對 Step 5 保持高度期待。

Step 5 Preview 技術架構全解析

稀疏 MoE：為什麼 600B 比你想的更便宜

「600B 參數」這個數字容易讓人以為 Step 5 的推論成本會高得嚇人。實際上，MoE（Mixture of Experts）架構讓這個假設不成立。

Step 5 的 600B 參數分布在多個「專家」（expert）子網路中。每次處理一個 token 時，路由器（router）只選擇其中幾個 expert 激活——Step 5 的設計是每 token 只啟動 27B 參數（4.5% 激活率）。

實際效果：Step 5 的推論延遲和每 token 成本，更接近一個 27B 的 dense 模型，而不是 600B 的 dense 模型。同樣架構在 Reflection Beam（501B/23B）和 Mistral Large 4（1T/49B）上也可以看到類似的設計邏輯。

Benchmark 數據：Step 5 站在哪裡？

根據 BenchLM 和 Artificial Analysis 的第三方評測（截至 2026 年 10 月），Step 5 Preview 的主要基準分數如下：

  • MCP Atlas（Agent 能力）：85.6%，對比最佳 Muse Spark 1.1 的 88.1%，差距約 2.5%
  • BrowseComp（網頁瀏覽推理）：88.7%，對比最佳 Atria Dawn Preview 的 92.5%，差距 3.8%
  • JobBench（職場任務）：59.0%，對比最佳 Muse Spark 1.3 的 64.9%，差距 5.9%
  • AutomationBench（自動化任務）：44.0%，對比最佳 DeepSeek V4.1 Flash 的 54.8%，差距 10.8%
評測小結：Step 5 在 agent-oriented 任務（MCP、BrowseComp）表現接近頂尖水平，但在自動化批次任務（AutomationBench）仍落後約 11%。這個模型最適合需要長上下文推理和多模態輸入的應用，而不是高吞吐量的批次自動化場景。

與競品的實際比較

StepFun 自家的 coding benchmark 顯示 Step 5 接近 GPT-6 Astra 和 Claude Opus 5，但低於兩者——這個說法需要一點背景。

首先，「接近頂尖」在 2026 年是什麼水準？對於絕大多數的商業應用（文件處理、程式碼生成、多輪對話、RAG），「接近頂尖」的模型已經綽綽有餘。真正需要頂尖效能的場景（例如 AIME 數學競賽、前沿科學研究）才需要 Claude Opus 5 或 GPT-6 Astra。

其次，Step 5 的競爭優勢不是純粹的效能，而是效能/成本比。$1.00/1M input、$2.70/1M output，比同等級的 Claude 便宜 3-5 倍。

API 現在就能用：快速上手教學

Step 5 API 目前已在 StepFun 的 Open Platform 上線，也可以透過 OpenRouter 存取（相容 OpenAI API 格式）。

方法一：直接使用 StepFun API

import openai

client = openai.OpenAI(
    base_url="https://api.stepfun.com/v1",
    api_key="YOUR_STEPFUN_API_KEY"
)

response = client.chat.completions.create(
    model="step-5-preview",
    messages=[
        {"role": "user", "content": "請分析這份程式碼的效能瓶頸並給出優化建議"}
    ],
    max_tokens=4096
)

print(response.choices[0].message.content)

方法二：透過 OpenRouter（支援統一 API）

import openai

client = openai.OpenAI(
    base_url="https://openrouter.ai/api/v1",
    api_key="YOUR_OPENROUTER_API_KEY"
)

response = client.chat.completions.create(
    model="stepfun/step-5-preview",
    messages=[
        {"role": "user", "content": "分析這張圖表並提取關鍵數據"}
    ]
)

print(response.choices[0].message.content)

控制 Reasoning 強度

Step 5 支援三種 reasoning 強度設定，讓你在速度和推理深度之間取得平衡：

# 快速回應（適合簡單問題）
response = client.chat.completions.create(
    model="step-5-preview",
    messages=[...],
    extra_body={"thinking": {"type": "enabled", "budget_tokens": 1000}}  # low
)

# 深度推理（適合複雜分析）
response = client.chat.completions.create(
    model="step-5-preview",
    messages=[...],
    extra_body={"thinking": {"type": "enabled", "budget_tokens": 10000}}  # high
)

適用情境分析：什麼時候選 Step 5？

✅ Step 5 最適合的場景

  • 長文件分析 RAG：1M token context 讓你可以把整份法律合約、技術規格書丟進去問問題
  • 多模態 Pipeline：文字 + 圖片 + 影片統一處理，不需要多個模型串接
  • 成本敏感的 agentic 任務：比 Claude Sonnet 便宜 3-5 倍，適合高頻次呼叫的 AI agent
  • 需要 reasoning 控制的場景：low/medium/high 讓你精確控制推理深度和 token 用量
  • 自架部署（Oct 15 後）：想要完全掌控資料隱私、不依賴第三方 API 的企業

❌ 可能不適合的場景

  • 高吞吐量自動化批次任務：AutomationBench 顯示 Step 5 在這個類別落後 DeepSeek V4.1 Flash 約 11%
  • 需要頂尖 coding 效能：如果你的使用案例需要最高品質的程式碼生成，Claude Opus 5 或 GPT-6 Astra 仍是更安全的選擇
  • 現有 Claude/OpenAI API 依賴很深：遷移成本可能抵消定價優勢

「Preview」兩個字代表什麼？你要知道的風險

StepFun 在模型名稱中加了「Preview」，這不是行銷用語——而是一個實質的警告。

目前的 step-5-preview 可能在正式版發布前發生以下變化：

  • 定價調整（上漲或下降）
  • API 行為改變（包括 reasoning 機制）
  • 速率限制變更
  • 模型名稱更改（正式版可能叫 step-5 而非 step-5-preview）
  • Open weights 授權條款最終確認

建議在生產環境中保持 mock 測試層，避免直接硬綁 step-5-preview 這個 model ID。

實戰測試：AutoDev AI 的使用心得

我們在過去兩週使用 Step 5 Preview API 處理了幾個實際工作任務，分享幾個觀察：

長文件摘要：把一份 150 頁的技術規格書（約 80K tokens）貼進去，Step 5 的摘要品質非常好，結構清晰，沒有出現「截斷式摘要」的問題。這個場景下，比 Claude Haiku 5.5 的品質好，比 Claude Sonnet 4.6 稍差但便宜很多。

程式碼 review：對一個約 2,000 行的 Python 專案進行程式碼審查。Step 5 識別出了 3 個真實的效能問題，以及 2 個安全疑慮。分析深度屬於「夠用」等級，但不如 Claude Opus 5 那麼細緻。

多輪對話穩定性：在 30 輪長對話中，Step 5 保持了良好的上下文連貫性。沒有出現「忘記之前說了什麼」的現象。

Reasoning 模式效果：high reasoning 模式在數學問題上明顯比 low 模式準確，但 token 消耗也多出 3-5 倍。建議只在確實需要深度推理的場景使用 high 模式。
